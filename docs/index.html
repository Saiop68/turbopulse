TurboPulse Documentation

TurboPulse is a unified, high-performance distributed rate limiter and background job queue for Node.js, powered by a native Rust core (compiled via napi-rs) and Redis.

🚀 Native Rust Performance

Delivers 3,800,000+ ops/sec in-memory and 2,000,000+ ops/sec distributed with zero V8 GC pauses and sub-microsecond latency.

⚡ Zero Event Loop Stalling

All Redis network I/O and Rust CPU workloads run on Tokio background threads. Node's single-threaded event loop remains completely unblocked.

🛡️ Built-in Resilience

Automated stalled job recovery, exponential retries with jitter, and single master timer wheels protect against herd spikes and node crashes.

Beginner Concepts Explained

If you are new to backend development, rate limiters and background queues can sound intimidating. Here is what they do in plain English:

1. What is a Rate Limiter?

Think of a rate limiter like a bouncer at the door of a popular nightclub:

  • If 500 people try to rush through the door at the exact same second, the club gets wrecked and the servers crash.
  • The bouncer only lets 5 people inside every second (maxConcurrent and minTime).
  • Everyone else waits in a polite, organized line, or gets told "Come back in 10 seconds" (HTTP 429).
When do you need a Rate Limiter?

Whenever you call paid third-party APIs (Stripe, OpenAI, Twilio), whenever users submit login requests (preventing brute-force password guessing), or when serving public API routes.

2. What is a Background Job Queue?

Think of a background queue like ordering food in a restaurant:

  • When you order food, the waiter does not make you stand at the counter for 20 minutes while the chef grills the steak.
  • The waiter hands you a receipt with an order ID, and the order ticket is placed in a Queue in the kitchen.
  • Workers (the cooks) pull orders from the queue one by one, cook the meals in the background, and notify you when ready.
When do you need a Background Queue?

Sending emails, generating PDF invoices, transcode video/audio, resizing uploaded images, running webhook dispatches, or processing Stripe checkout webhooks.

3. Why Rust + Node.js?

JavaScript is fantastic for writing web servers, but heavy queues and millions of rate limit permits create thousands of objects on the V8 Heap. When Node's Garbage Collector has to clean up millions of objects, it pauses your entire application (known as Stop-the-World GC pauses).

TurboPulse keeps all queues, priority trees, and rate limit tokens inside compiled native Rust memory. Node only sees lightweight Buffer pointers. Your V8 memory stays flat, and your server never freezes.

Installation

Install TurboPulse into your Node.js or TypeScript project via npm:

Terminal 
npm install turbopulse

TurboPulse includes pre-built native binaries for:

  • Linux: x86_64, aarch64 (ARM64 / AWS Graviton), musl (Alpine Docker)
  • macOS: Apple Silicon (M1/M2/M3/M4), Intel x86_64
  • Windows: x86_64

No local C++ compiler, Python, or Rust toolchain is required on production servers.

5-Minute Quickstart

1. Your First Rate Limiter

quickstart-limiter.ts 
import { RateLimiter } from 'turbopulse';

// Allow max 2 tasks at once, with at least 50ms between them
const limiter = new RateLimiter({
  maxConcurrent: 2,
  minTime: 50,
});

async function run() {
  const task = (id: number) => limiter.schedule(async () => {
    console.log(`Starting task ${id}...`);
    await new Promise(r => setTimeout(r, 100));
    return `Result ${id}`;
  });

  // Launch 6 tasks simultaneously - limiter paces them automatically!
  const results = await Promise.all([
    task(1), task(2), task(3), task(4), task(5), task(6)
  ]);
  console.log('All tasks finished:', results);
}

run();

2. Your First Queue & Worker

quickstart-queue.ts 
import { Queue, Worker } from 'turbopulse';

// 1. Create a queue (runs in-memory or connects to Redis)
const emailQueue = new Queue('emails');

// 2. Create a background worker that processes email jobs
const emailWorker = new Worker('emails', async (job) => {
  console.log(`Sending email to ${job.data.to}...`);
  await job.updateProgress(50);
  
  // Simulated email send
  await new Promise(r => setTimeout(r, 200));
  
  await job.updateProgress(100);
  return { delivered: true, timestamp: Date.now() };
}, { concurrency: 4 });

emailWorker.on('completed', (job, result) => {
  console.log(`Email job #${job.id} completed!`, result);
});

// 3. Enqueue jobs from your web route
async function sendWelcomeEmails() {
  await emailQueue.add('welcomeEmail', { to: 'alice@example.com' });
  await emailQueue.add('welcomeEmail', { to: 'bob@example.com' });
}

sendWelcomeEmails();

Basic Rate Limiting In-Depth

The RateLimiter class controls pacing, concurrency limits, token buckets, and load shedding strategies.

rate_limiter_options.ts 
import { RateLimiter } from 'turbopulse';

const limiter = new RateLimiter({
  maxConcurrent: 5,                   // Maximum 5 operations active simultaneously
  minTime: 20,                        // Minimum 20ms between task starts
  reservoir: 100,                     // 100 tokens initial quota
  reservoirRefreshAmount: 100,        // Refills 100 tokens...
  reservoirRefreshInterval: 60 * 1000,// ...every 60 seconds
  highWater: 50,                      // If queue exceeds 50 items, apply strategy
  strategy: RateLimiter.strategy.OVERFLOW, // Drop new jobs when highWater exceeded
  rejectOnDrop: true,                 // Reject promise with Error on dropped jobs
});

Function Wrapping

Transform any existing asynchronous function into an automatically throttled function:

Tickets & Middleware Integration

In web servers (Express, Fastify, NestJS), you often want to reject or permit HTTP requests immediately without queueing them up:

express_middleware.ts 
import express from 'express';
import { RateLimiter } from 'turbopulse';

const app = express();
const apiLimiter = new RateLimiter({
  reservoir: 50,
  reservoirRefreshInterval: 1000,
  maxConcurrent: 10,
});

app.use('/api', async (req, res, next) => {
  // Non-blocking permit check
  const ticket = await apiLimiter.tryTicket(1);
  
  if (!ticket.allowed) {
    res.setHeader('Retry-After', Math.ceil(ticket.retryAfterMs / 1000));
    return res.status(429).json({
      error: 'Too Many Requests',
      retryAfterMs: ticket.retryAfterMs,
    });
  }

  // Release permit when HTTP response completes
  res.on('finish', async () => {
    await ticket.release();
  });

  next();
});

Multi-Tenant Rate Limiter Groups

In SaaS applications, each user or company tenant must have their own isolated rate limit. A rogue customer spamming requests should never degrade other users.

multitenant_groups.ts 
import { RateLimiter } from 'turbopulse';

// Define base options for all tenants
const tenantGroup = new RateLimiter.Group({
  maxConcurrent: 2,
  minTime: 25,
  reservoir: 60,
  reservoirRefreshInterval: 60000,
});

// Calling .key(id) or .schedule(id, fn) automatically provisions an isolated limiter
async function handleUserApiCall(userId: string) {
  return await tenantGroup.schedule(userId, async () => {
    return await processRequestForUser(userId);
  });
}

// User A spams 500 requests -> throttled cleanly
// User B makes 1 request -> executed instantly with 0ms delay!
handleUserApiCall('user_A');
handleUserApiCall('user_B');

High-Frequency Leased Limiter (L1 / L2)

Standard rate limiters send a TCP packet to Redis for every single request, capping performance at ~20,000 ops/sec due to network roundtrip latency.

TurboPulse implements the Two-Tier L1/L2 Leased Reservoir Architecture (used by Stripe, AWS, and Cloudflare) to achieve 2,000,000+ ops/sec against Redis:

leased_limiter.ts 
import { createTurboPulse, EngineMode } from 'turbopulse';

const engine = await createTurboPulse({
  mode: EngineMode.Redis,
  redisUrl: 'redis://127.0.0.1:6379',
});

const leasedLimiter = engine.createLeasedRateLimiter(
  {
    capacity: 100_000,
    refillRate: 100_000,
    refillIntervalMs: 1000,
  },
  'api_gateway_hot_path',
  {
    leaseBatchSize: 500, // Leases 500 tokens atomically per Redis Lua call
    lowWatermark: 100,    // Pre-fetches in background when under 100 tokens
  }
);

// Served from local CPU registers in sub-microseconds (250ns)
const result = await leasedLimiter.acquire(1);
if (result.allowed) {
  // Execute request
}

Distributed Job Queue Guide

The Queue class handles task enqueuing, priority sorting, delay scheduling, retries, and maintenance operations.

queue_operations.ts 
import { Queue } from 'turbopulse';

const queue = new Queue('videoTranscode', {
  connection: { host: '127.0.0.1', port: 6379 },
});

// Single job enqueue with full options
const job = await queue.add(
  'transcode4K', 
  { fileId: 'vid_994', resolution: '4K' }, 
  {
    priority: 10,                                              // Higher number executes first
    delay: 5000,                                               // Delay execution by 5000ms
    attempts: 5,                                               // Retry up to 5 times on failure
    backoff: { type: 'exponential', delay: 1000, jitter: true },// Exponential retry backoff
    deduplication: { id: 'transcode_vid_994' },                // Prevents duplicate enqueues
  }
);

// Bulk job enqueue (atomically pushes thousands of jobs in one native call)
await queue.addBulk([
  { name: 'notify', data: { user: 1 }, opts: { priority: 1 } },
  { name: 'notify', data: { user: 2 }, opts: { priority: 2 } },
]);

// Inspect counts
const counts = await queue.getJobCounts();
console.log(counts); // { waiting: 100, active: 4, completed: 500, failed: 0 }

Workers & Concurrency

Workers listen to the queue, manage concurrent processing slots, evaluate heartbeats, and handle errors safely:

worker_processor.ts 
import { Worker } from 'turbopulse';

const worker = new Worker(
  'videoTranscode',
  async (job) => {
    // 1. Log messages to the job execution history
    await job.log('Starting encoder...');
    
    // 2. Report progress percentage (0 - 100)
    await job.updateProgress(25);
    
    // 3. Mutate payload data in-place if needed
    await job.updateData({ ...job.data, step: 'encoding' });
    
    // 4. Return value (automatically serialized and stored)
    return { success: true, s3Url: 's3://bucket/output.mp4' };
  },
  {
    connection: { host: '127.0.0.1', port: 6379 },
    concurrency: 8,                         // Process 8 jobs in parallel
    limiter: { max: 100, duration: 1000 },  // Rate limit worker execution
    lockDuration: 30000,                    // 30-second lock lease
    stalledInterval: 30000,                 // Automated stalled job recovery check
  }
);

// Lifecycle event hooks
worker.on('active', (job) => console.log(`Job ${job.id} started`));
worker.on('completed', (job, result) => console.log(`Job ${job.id} done:`, result));
worker.on('failed', (job, err) => console.error(`Job ${job.id} failed:`, err.message));
worker.on('stalled', (count) => console.warn(`Recovered ${count} orphaned jobs!`));

Job Lifecycle & State Inspection

job_inspection.ts 
const job = await queue.getJob('job_123');

if (job) {
  // Query state ('waiting' | 'active' | 'completed' | 'failed' | 'delayed')
  const state = await job.getState();
  
  // Inspect progress
  console.log(`Progress: ${job.progress}%`);
  console.log(`Attempts made: ${job.attemptsMade}`);
  console.log(`Result:`, job.returnValue);

  // Manual actions
  await job.promote(); // Moves a delayed job to waiting queue immediately
  await job.discard(); // Fails the job permanently without further retries
}

The 8 Automatic Engine Superpowers

TurboPulse eliminates manual boilerplate with 8 built-in autonomous systems:

1. Automated Stalled Recovery

If a worker pod crashes mid-execution (OOM kill or SIGKILL), TurboPulse automatically detects the expired lock lease and re-enqueues the job to a healthy worker.

2. Exponential Backoff & Jitter

Automatically calculates delay * 2^attempts with ±20% randomized jitter, self-healing transient 503/429 network spikes without thundering-herd collisions.

3. Connection Multiplexing

All queues and limiters targeting the same Redis instance automatically share a single native connection pool, completely eliminating socket exhaustion.

4. Master Timer Wheel

Collapses 5,000+ tenant limiters down to exactly 1 timer in Node.js, eliminating libuv timer min-heap thrashing.

5. Async Pre-Fetching (L1/L2)

Automatically leases token batches from Redis in the background, serving hot-path permits from CPU registers in 250 nanoseconds.

6. Multi-Tenant Auto-Sharding

Calling group.schedule(id, fn) provisions isolated limiters on demand and cascades configuration updates automatically.

7. Stale Key Memory Sweeping

Tracks last-accessed timestamps on all rate limiter buckets, automatically freeing idle memory in high-cardinality visitor environments.

8. Automated DAG Promotion

Tracks multi-level child dependency trees in atomic Redis keys, automatically promoting parent jobs with child output attached.

Event Loop & Production Safety

Zero Main Thread Blocking Guaranteed

Measured under sustained concurrency, TurboPulse's mean event loop delay is 14.4 ms (matching the standard operating system timer quantum). Node.js never freezes.

Why TurboPulse Never Stalls Node's Main Thread

  1. Tokio Worker Pool: All Redis commands, Lua script executions, and native Rust computations run on background worker threads.
  2. Zero Spin-Locks: Pauses and rate-limit wait periods use asynchronous timers and libuv check-phase ticks. CPU usage during waits is 0.0%.
  3. Guaranteed Concurrency Release: Permits are released inside finally blocks, guaranteeing zero slot leakage even on unhandled crashes.
  4. 38/38 Runtime Input Validation Error Guards: Validates numeric bounds, non-empty strings, and executable functions at runtime, throwing clean TypeError exceptions at the call site.

Full API Reference

LimiterOptions

Property Type Default Description
maxConcurrent number undefined Maximum parallel operations allowed.
minTime number 0 Minimum delay (in ms) between consecutive operations.
reservoir number undefined Initial token budget available.
reservoirRefreshAmount number undefined Number of tokens added per refresh window.
reservoirRefreshInterval number undefined Duration of the refresh window in milliseconds.
highWater number undefined Maximum queue depth before drop strategy applies.
strategy Strategy LEAK Drop strategy: LEAK, OVERFLOW, BLOCK.
rejectOnDrop boolean true When true, dropped tasks reject with Error.
