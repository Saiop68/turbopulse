turbopulse

A native rate limiter and distributed background job queue engine for Node.js, built with compiled Rust (via napi-rs) and Redis.

Native Memory Model

Queue items and token reservoirs reside directly in Rust heap memory. Job data is transferred via zero-copy Node.js Buffers to prevent V8 Garbage Collection pauses.

Non-Blocking Execution

All native Rust computations and Redis network I/O run on background Tokio worker threads, returning standard Promises that immediately yield to the libuv event loop.

Resilience & Recovery

Built-in distributed lock expiration heartbeats, exponential retries with jitter, and a single master timer wheel to avoid libuv timer min-heap overhead.

Core Concepts

1. What is Rate Limiting?

Rate limiting restricts how frequently an action or function can be executed over time (e.g. max 100 requests per minute, or max 5 concurrent operations). It protects APIs from exhaustion, prevents brute-force login attempts, and keeps third-party API bills under control.

2. What is a Background Job Queue?

In web servers, long-running operations (such as processing images, delivering emails, or compiling reports) should not block the HTTP request-response cycle. A queue stores the task payload, allows the API to respond immediately to the client with a 200/202 status, and delegates execution to asynchronous background workers.

3. Why Native Rust instead of Pure JavaScript?

Pure JavaScript implementations store jobs and rate-limit counters as JavaScript objects on the V8 heap. Under high throughput (thousands of tasks per second), V8's Garbage Collector must periodically pause the entire application to clean up temporary objects. TurboPulse stores queue records and tokens in native Rust memory, completely bypassing V8 GC pressure.

Installation

Install via npm:

bash 
npm install turbopulse

Pre-compiled native binaries are bundled for:

  • Linux: x86_64, aarch64 (ARM64 / AWS Graviton), musl (Alpine Docker)
  • macOS: Apple Silicon (M1/M2/M3/M4), Intel x86_64
  • Windows: x86_64

No local C++ compiler, Python, or Rust toolchain is required on client or production machines.

Quickstart

1. Rate Limiting Example

rate_limiter_quickstart.ts 
import { RateLimiter } from 'turbopulse';

// Limit execution to 2 concurrent tasks with at least 50ms spacing
const limiter = new RateLimiter({
  maxConcurrent: 2,
  minTime: 50,
});

async function run() {
  const task = (id: number) => limiter.schedule(async () => {
    await new Promise(r => setTimeout(r, 100));
    return `Task ${id} completed`;
  });

  const results = await Promise.all([
    task(1), task(2), task(3), task(4)
  ]);
  console.log(results);
}

run();

2. Background Queue & Worker Example

queue_quickstart.ts 
import { Queue, Worker } from 'turbopulse';

// 1. Create a queue
const emailQueue = new Queue('emails');

// 2. Register worker to process tasks
const emailWorker = new Worker('emails', async (job) => {
  await job.updateProgress(50);
  // Perform background work
  await job.updateProgress(100);
  return { delivered: true, recipient: job.data.to };
}, { concurrency: 4 });

emailWorker.on('completed', (job, result) => {
  console.log(`Job #${job.id} finished:`, result);
});

// 3. Enqueue jobs
await emailQueue.add('welcomeEmail', { to: 'user@example.com' });

Engine Modes & Factory

TurboPulse can be used directly via high-level classes (new RateLimiter(), new Queue()) or instantiated through the low-level TurboPulse factory for centralized resource pooling.

Available Engine Modes

  • EngineMode.InMemory: Operates entirely inside compiled Rust heap memory with lock-free concurrent hash maps. Zero external dependencies, ideal for single-instance applications, unit tests, and CLI tools.
  • EngineMode.Redis: Executes atomic Lua scripts across distributed Redis instances or Redis clusters, guaranteeing multi-node consistency.
engine_factory.ts 
import { createTurboPulse, createInMemoryTurboPulse, EngineMode } from 'turbopulse';

// 1. Asynchronous Redis initialization
const redisEngine = await createTurboPulse({
  mode: EngineMode.Redis,
  redisUrl: 'redis://127.0.0.1:6379',
  keyPrefix: 'my_app',
  redisPoolSize: 10,
});

// Create limiters and queues sharing the engine's connection pool
const limiter = redisEngine.createRateLimiter({
  capacity: 1000,
  refillRate: 1000,
  refillIntervalMs: 1000,
}, 'api_gateway');

const queue = redisEngine.createQueue('transcoding');

// 2. Synchronous local In-Memory engine
const localEngine = createInMemoryTurboPulse();
const localLimiter = localEngine.createRateLimiter({ capacity: 50 });

TurboPulse automatically normalizes Redis targets from raw URLs, existing ioredis clients, node-redis instances, or plain connection options ({ host, port, password, tls }).

RateLimiter API

The RateLimiter class controls concurrency limits, execution spacing, token reservoirs, and load shedding strategies.

1. Priority Scheduling & Job Options

Jobs can specify priority (0 = highest priority, 9 = lowest priority), token weight, and execution deadlines:

limiter_scheduling.ts 
import { RateLimiter } from 'turbopulse';

const limiter = new RateLimiter({
  maxConcurrent: 5,                   // Maximum parallel tasks
  minTime: 20,                        // Minimum delay (ms) between consecutive starts
  reservoir: 100,                     // Initial quota
  reservoirRefreshAmount: 100,        // Tokens replenished...
  reservoirRefreshInterval: 60 * 1000,// ...per interval (60 seconds)
  highWater: 50,                      // Queue threshold before strategy activates
  strategy: RateLimiter.strategy.OVERFLOW, // Drop incoming tasks when queue is full
  rejectOnDrop: true,                 // Reject promise with Error on dropped tasks
});

// High-priority task with custom token weight and 5s expiration deadline
const result = await limiter.schedule(
  {
    priority: 0,        // Highest priority
    weight: 2,          // Consumes 2 tokens from reservoir
    expiration: 5000,   // Fails if waiting longer than 5000ms
    id: 'charge_req_42'
  },
  async () => {
    return await chargeCreditCard();
  }
);

// Wrapping functions:
const safeFetch = limiter.wrap(fetch, { priority: 2 });
const response = await safeFetch('https://api.example.com/data');

// Node.js callback-style execution:
limiter.submit(
  async (cb) => {
    const data = await readDatabase();
    cb(null, data);
  },
  (err, data) => {
    if (err) console.error(err);
  }
);

2. Shedding Strategies

When the waiting queue depth reaches highWater, TurboPulse executes one of three strategies:

  • RateLimiter.strategy.LEAK (Default): Drops the lowest-priority waiting task in the queue to make room for the new task.
  • RateLimiter.strategy.OVERFLOW: Immediately drops the incoming task without touching already queued tasks.
  • RateLimiter.strategy.BLOCK: Empties and rejects all currently queued tasks and rejects all incoming tasks until traffic ceases.

Non-Blocking Tickets & Middleware

In HTTP frameworks (Express, Fastify, Next.js), you often need to verify rate limits and concurrency instantly without holding the request in an internal queue.

express_middleware.ts 
import express from 'express';
import { RateLimiter } from 'turbopulse';

const app = express();
const limiter = new RateLimiter({
  reservoir: 100,
  reservoirRefreshInterval: 60000,
  maxConcurrent: 20,
});

app.use('/api', async (req, res, next) => {
  // 1. Non-blocking ticket evaluation
  const ticket = await limiter.tryTicket(1);
  
  if (!ticket.allowed) {
    res.setHeader('Retry-After', Math.ceil((ticket.retryAfterMs || 1000) / 1000));
    return res.status(429).json({
      error: 'Too Many Requests',
      retryAfterMs: ticket.retryAfterMs,
    });
  }

  // 2. Guaranteed concurrency release on response termination
  res.on('finish', async () => {
    await ticket.release(); // Decrements active concurrency slot
  });

  next();
});

// Peeking token availability without consuming:
const hasQuota = await limiter.check(1); // true if 1 token available, false otherwise

For operations that should pause and wait in line until capacity is free, use await limiter.getTicket(weight), which suspends execution until permits become available.

Reservoirs & Chaining

1. Dynamic Reservoir Inspection & Mutation

Inspect or modify the current token budget in real time without restarting the limiter:

reservoir_mutation.ts 
const currentTokens = await limiter.currentReservoir();
console.log('Available tokens:', currentTokens);

// Manually grant bonus tokens or credit
await limiter.incrementReservoir(50);

// Dynamically update limiter options at runtime
limiter.updateSettings({
  maxConcurrent: 10,
  minTime: 10,
});

2. Multi-Tier Limiter Chaining

Enforce multiple independent constraints simultaneously (for instance, limiting an external integration to 10 requests per second AND 500 requests per minute):

limiter_chaining.ts 
import { RateLimiter } from 'turbopulse';

// Tier 1: Per-second smoothing
const perSecondLimiter = new RateLimiter({
  reservoir: 10,
  reservoirRefreshAmount: 10,
  reservoirRefreshInterval: 1000,
});

// Tier 2: Per-minute hard ceiling
const perMinuteLimiter = new RateLimiter({
  reservoir: 500,
  reservoirRefreshAmount: 500,
  reservoirRefreshInterval: 60 * 1000,
});

// Chain: perSecondLimiter requires perMinuteLimiter approval before execution
perSecondLimiter.chain(perMinuteLimiter);

// Scheduling via perSecondLimiter now satisfies BOTH constraints automatically
await perSecondLimiter.schedule(() => callThirdPartyApi());

3. Graceful Shutdown

shutdown.ts 
// Stops the limiter and drops pending queue items with an Error
await limiter.stop({ dropWaitingJobs: true, enqueueErrorMessage: 'Limiter stopped for deployment' });

Multi-Tenant Groups

Isolate rate limits per user, organization, or API key with shared base configuration:

groups.ts 
import { RateLimiter } from 'turbopulse';

const group = new RateLimiter.Group({
  maxConcurrent: 2,
  minTime: 25,
  reservoir: 60,
  reservoirRefreshInterval: 60000,
});

// Calling .schedule(id, fn) provisions an isolated limiter on first access
async function handleUserApiCall(userId: string) {
  return await group.schedule(userId, async () => {
    return await executeQuery(userId);
  });
}

// User A's traffic spike has zero impact on User B
handleUserApiCall('org_stripe');
handleUserApiCall('org_github');

// Direct instance management:
const orgLimiter = group.key('org_stripe');       // Access or instantiate instance
const activeKeys = group.limiters();              // Returns array of all active tenant keys
await group.deleteKey('org_stripe');              // Stops limiter and removes key
group.cleanup(300000);                            // Evicts idle tenant limiters older than 5 minutes

Two-Tier Leased Limiter (L1 / L2)

Standard distributed rate limiters issue a network roundtrip to Redis for every token check, bounding single-thread throughput to ~20,000 ops/sec due to TCP network latency.

TurboPulse provides a Two-Tier L1/L2 Leased Architecture to achieve 2,000,000+ ops/sec against Redis:

leased_limiter.ts 
import { createTurboPulse, EngineMode } from 'turbopulse';

const engine = await createTurboPulse({
  mode: EngineMode.Redis,
  redisUrl: 'redis://127.0.0.1:6379',
});

const leasedLimiter = engine.createLeasedRateLimiter(
  {
    capacity: 100_000,
    refillRate: 100_000,
    refillIntervalMs: 1000,
  },
  'gateway_route',
  {
    leaseBatchSize: 500, // Leases 500 tokens per atomic Redis Lua roundtrip
    lowWatermark: 100,    // Pre-fetches in background when under 100 tokens
  }
);

// Served from local CPU registers in 250 nanoseconds
const permit = await leasedLimiter.acquire(1);

// Ultra-fast zero-overhead synchronous check:
if (leasedLimiter.acquireFast(1)) {
  // Executed with sub-microsecond latency
}

Limiter Events & Metrics

The RateLimiter class extends Node.js EventEmitter and emits fine-grained operational events:

limiter_events.ts 
limiter.on('idle', () => console.log('Limiter is fully idle (queue and concurrency are 0)'));
limiter.on('empty', () => console.log('Waiting queue has emptied'));
limiter.on('depleted', (res) => console.warn(`Tokens exhausted. Wait time: ${res.retryAfterMs}ms`));
limiter.on('dropped', (task) => console.warn(`Task ${task.id} dropped by strategy`));
limiter.on('error', (err) => console.error('Limiter error:', err));

// Inspect real-time execution metrics:
const counts = limiter.counts();
console.log({
  executing: counts.EXECUTING, // Currently running
  queued: counts.QUEUED,       // Waiting in queue
  done: counts.DONE,           // Total completed
  failed: counts.FAILED,       // Total failed
});

Queue Operations & Management

queue_methods.ts 
import { Queue } from 'turbopulse';

const queue = new Queue('transcode', {
  connection: { host: '127.0.0.1', port: 6379 },
});

await queue.waitUntilReady();

// 1. Enqueue job with advanced options
const job = await queue.add(
  'encodeJob', 
  { file: 'video.mp4', resolution: '1080p' }, 
  {
    priority: 10,                                              // Higher number = higher priority
    delay: 5000,                                               // Delay execution by 5000ms
    attempts: 4,                                               // Max retry attempts on failure
    backoff: { type: 'exponential', delay: 1000, jitter: true },// Exponential retry backoff
    deduplication: { id: 'file_video_mp4' },                   // Deduplication key
    timeout: 60000,                                            // Job timeout limit in ms
    removeOnComplete: true,                                    // Auto-cleanup on success
  }
);

// 2. Atomic bulk enqueue
const batchJobs = await queue.addBulk([
  { name: 'taskA', data: { id: 1 }, opts: { priority: 5 } },
  { name: 'taskB', data: { id: 2 }, opts: { priority: 1 } },
]);

// 3. Queue inspection & dashboard metrics
const counts = await queue.getJobCounts();
console.log(`Waiting: ${counts.waiting}, Active: ${counts.active}, Delayed: ${counts.delayed}, Failed: ${counts.failed}`);

// 4. Lifecycle controls
await queue.pause();
console.log('Is queue paused:', await queue.isPaused());
await queue.resume();

// 5. Maintenance & Pruning
await queue.clean(60000, 1000, 'completed'); // Clean completed jobs older than 60s
await queue.drain();                         // Empties waiting queue
await queue.obliterate();                    // Completely purges all queue data
await queue.close();                         // Releases connections

Workers & Concurrency

worker_setup.ts 
import { Worker } from 'turbopulse';

const worker = new Worker(
  'transcode',
  async (job) => {
    await job.log('Starting execution');
    await job.updateProgress(25);
    
    // Process task data
    const result = await processFile(job.data);
    
    await job.updateProgress(100);
    return result;
  },
  {
    connection: { host: '127.0.0.1', port: 6379 },
    concurrency: 8,                         // 8 parallel execution slots
    limiter: { max: 100, duration: 1000 },  // Rate limit worker execution
    lockDuration: 30000,                    // 30s lock before treated as stalled
    lockRenewTime: 15000,                   // Heartbeat renews lock every 15s
    stalledInterval: 30000,                 // Stalled job recovery heartbeat
    maxStalledCount: 3,                     // Max recovery attempts before permanent failure
  }
);

// Worker lifecycle events:
worker.on('active', (job) => console.log(`Job #${job.id} is now active`));
worker.on('completed', (job, result) => console.log(`Job #${job.id} completed:`, result));
worker.on('failed', (job, err) => console.error(`Job #${job.id} failed:`, err.message));
worker.on('stalled', (count) => console.warn(`Recovered ${count} stalled jobs`));
worker.on('drained', () => console.log('All queue items processed'));
worker.on('error', (err) => console.error('Worker error:', err));

// Lifecycle management:
await worker.pause();
console.log('Worker paused:', worker.isPaused());
await worker.resume();
await worker.close(); // Gracefully waits for active jobs to finish before closing

Job Lifecycle & State

The Job instance represents an individual work payload with progress tracking, state checks, and payload mutation capabilities.

job_lifecycle.ts 
const job = await queue.getJob('job_123');

if (job) {
  // State inspection:
  const state = await job.getState(); // 'waiting' | 'active' | 'completed' | 'failed' | 'delayed'
  const isDone = await job.isCompleted();
  const isFailed = await job.isFailed();

  // Properties:
  console.log(`Job ID: ${job.id}`);
  console.log(`Created at: ${new Date(job.timestamp).toISOString()}`);
  console.log(`Attempts made: ${job.attemptsMade}`);
  console.log(`Progress: ${job.progress}%`);
  console.log(`Result:`, job.returnValue);

  // In-flight mutations & logging:
  await job.updateProgress(75);
  await job.updateData({ ...job.data, status: 'step_2_completed' });
  await job.log('Step 2 validation succeeded');

  // Manual scheduling overrides:
  await job.promote(); // Immediately promotes delayed job to waiting queue
  await job.retry();   // Re-enqueues failed job
  await job.discard(); // Permanently fails the job without further retries
}

QueueEvents & RPC Waiting

The QueueEvents class listens to distributed job state changes across remote worker nodes. It enables the distributed RPC pattern where an API gateway enqueues a job and suspends until the background worker finishes processing.

queue_events_rpc.ts 
import { Queue, QueueEvents } from 'turbopulse';

const queue = new Queue('reports', { connection: { host: '127.0.0.1', port: 6379 } });
const queueEvents = new QueueEvents('reports', { connection: { host: '127.0.0.1', port: 6379 } });

// Distributed RPC pattern:
async function generateReportSync(userId: string) {
  const job = await queue.add('generatePdf', { userId });

  // Suspends until remote worker finishes and returns the job's return value
  const pdfUrl = await queueEvents.waitForJob(job.id, 'completed', 30000);
  return pdfUrl;
}

// Global queue event streaming:
queueEvents.on('completed', ({ jobId, returnvalue }) => {
  console.log(`Remote job ${jobId} finished with result:`, returnvalue);
});

queueEvents.on('failed', ({ jobId, failedReason }) => {
  console.error(`Remote job ${jobId} failed:`, failedReason);
});

queueEvents.on('progress', ({ jobId, data }) => {
  console.log(`Remote job ${jobId} reported progress:`, data);
});

Automated Systems

TurboPulse handles resilience, connection lifecycles, and scheduling automatically:

Stalled Job Recovery

If a worker node crashes mid-execution (OOM kill or SIGKILL), TurboPulse detects the expired lock lease and re-enqueues the job to a healthy worker.

Exponential Backoff & Jitter

Calculates delay * 2^attempts with ±20% randomized jitter, preventing thundering-herd synchronization spikes on downstream services.

Connection Multiplexing

All queues and limiters targeting the same Redis instance share a single native connection pool, eliminating client socket exhaustion.

Hierarchical Timer Wheel

Collapses thousands of tenant rate limit schedules into 1 master timer in Node.js, eliminating libuv timer min-heap thrashing.

Asynchronous Token Pre-fetching

Leases token batches from Redis in the background, serving hot-path permits from local memory in 250 nanoseconds.

Multi-Tenant Auto-Provisioning

Calling group.schedule(id, fn) provisions isolated limiters on demand and cascades configuration updates across active instances.

Stale Key Sweeping

Tracks last-accessed timestamps on rate limiter buckets, freeing idle memory in high-cardinality visitor environments.

DAG Dependency Resolution

Tracks multi-level child dependency trees in atomic Redis keys, automatically promoting parent jobs with child output attached.

Event Loop Guarantees

Non-Blocking Event Loop Verification

Under continuous load, TurboPulse's mean event loop delay is 14.4 ms (matching the operating system baseline timer quantum). Node.js never stalls.

  1. Tokio Worker Pool: All native Rust computations and Redis network I/O run on background Tokio worker threads.
  2. Zero Spin-Locks: Wait periods use asynchronous timers and libuv check-phase ticks. CPU usage during waits is 0.0%.
  3. Guaranteed Concurrency Release: Permits are released inside finally blocks, guaranteeing zero slot leakage even on unhandled exceptions.
  4. Runtime Input Validation Guards: Validates numeric bounds, non-empty strings, and executable functions at runtime, throwing clean TypeError exceptions at call sites.
